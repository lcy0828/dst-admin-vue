# 前端分支收口与功能迁移

## 分支角色

| 分支 | 角色 | 处理方式 |
| --- | --- | --- |
| `master` | 正式 Vue 3 产品主线 | 所有后续前端开发和发布基于此分支 |
| `legacy/vue2-original` | 原始 Vue 2 保护分支 | 固定在 `527c140b66f5`，只用于追溯，不继续开发 |
| `feature/vue3-in-place` | Vue 3 升级期间的过渡名称 | 暂时保留为 `master` 的同提交别名，稳定后可删除 |
| `feature/v2-rebuild` | 另一套重构实验 | 不合并分支，只迁移经过审查的功能 |

`feature/vue3-in-place` 比原始 Vue 2 `master` 多 157 个已提交改动；收口前又补入了运行登记、玩家多房间容错、存档替换保护和旧任务组标识兼容。最终通过快进方式晋升为新的 `master`，没有制造无意义的合并提交。

## 为什么不能直接合并 v2-rebuild

两条功能分支都从 `527c140b` 开始独立重建。`feature/v2-rebuild` 使用另一套路由、页面目录、TypeScript API 客户端和应用外壳。普通 merge、rebase 或整批 cherry-pick 会同时引入两套页面并重新造成以下问题：

- `/mods/list`、`/servers/commands` 等正式路由被缺功能的路由表替换。
- 当前多语言、地图、模组和保留原布局的 shadcn-vue 页面被另一套 UI 覆盖。
- JavaScript 适配器和 TypeScript API 客户端并存，形成重复的数据与错误处理协议。
- 测试通过只能证明实验分支自身一致，不能证明正式产品功能没有减少。

因此采用“功能移植”而不是“Git 历史合并”：先写当前主线的回归测试，再按当前 API、i18n 和 UI 结构重写所需能力。

### 禁止迁移

- `AppShell.vue`、`src/router/index.ts` 和重构分支的整套路由。
- `RoomModsView.vue`、`WorldConsoleView.vue` 等实验页面整体。
- `src/api/client.ts`、生成的 `schema.d.ts` 和当前 JavaScript 适配器并存。
- 实验分支的基础 shadcn 组件、全局 CSS、Tailwind 配置和 package 配置。
- 任何以“提交更新”或“构建通过”为唯一依据的整目录服务切换。

## 可选方案比较

| 方案 | 结果 | 结论 |
| --- | --- | --- |
| 普通 merge | 冲突多，保留两套应用结构 | 不采用 |
| rebase v2-rebuild | 仍会重放不需要的重造提交 | 不采用 |
| 整批 cherry-pick | 会复制实验路由、组件和客户端 | 不采用 |
| 单提交 cherry-pick | 提交强依赖实验结构，后续维护困难 | 原则上不采用 |
| 按功能重写移植 | 保留正式 UI、路由、i18n 和 API 边界 | 采用 |
| 后端能力驱动生成客户端 | 长期可减少接口漂移 | 后续独立规划，不与本次分支收口混做 |

## 合入与发布门禁

1. 新功能先在 `master` 上增加正式页面的回归测试。
2. 每个迁移能力单独提交，不使用“同步 v2 分支”式大提交。
3. 每批至少通过 lint、单测和生产构建。
4. Runtime 能力还需要连接当前 `8000` 后端做非破坏性实机验收。
5. 发布或重启前核对 `5173` 的 cwd、分支、关键路由以及未受影响服务 PID。
